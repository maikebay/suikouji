# 用户可读回复与固定报表方案

这份方案记录用户截图暴露的产品问题和下一步实现边界。当前已实现能力契约中的展示要求；下述固定报表接口、模板渲染器和内置iLink模型整理层尚未实现。

## 当前问题

用户需要知道正在核对什么业务数据，看到收支情况和缺少哪些记录。`entries / sales / summary`、`gross=None`、接口路由、分页次数与服务器路径属于内部信息，不适合直接充当进度或报表。只要求Agent“写好看一点”不能固定统计口径和输出结构。

## 产品控制的三层

1. **报表数据**：产品按已授权账本、明确时间范围和金额口径查询现有业务表。保留当前日总额与销售明细的去重规则，财务汇总不回加派生观测。统一返回指标、覆盖情况、未知值原因和警告；Agent不自行对原始分页重算收入。
2. **展示模板**：产品固定中文名称、顺序、货币格式、缺失值说明和可读内容。同一份数据渲染成微信纯文本或网页/文件；渲染器不改变金额，也不引入模型调用。
3. **Agent解释**：Agent选择报表类型和时间范围，先说明正在查什么，返回工具已生成的报表；可补充有依据的解释，不能改金额、把差额说成利润或编造因果。用户明确要原始明细时，才另行提供。

建议第一种报表只做经营收支概览，复用已有summary/账目/销量查询。拟议的只读报表入口返回 `report_version`、账本和统计范围、指标、数据覆盖、警告、渲染后的微信文本及可选Markdown。具体HTTP路径、文件下载和分页策略在实施时定稿，不能当作当前可调用接口。

## 固定输出规则

- 抬头为账本名称、报表类型、日期范围；没有指定范围时，说明采用的范围。不能默认将所有历史数据称为本月。
- 主体依次为营业收入、采购付款、费用付款、收支差额。人民币金额保留两位小数和千位分隔。
- 差额公式为已记收入减采购付款及费用付款；持续标明它不等于利润。实际耗料成本、库存等依据缺失时，利润写“暂无法计算”，说明缺项。
- 可选部分展示主要支出、商品销售和待补充信息。有销量但无销售金额时，只报数量并说明金额未记录。
- 未知、未记录和实际为零是不同状态。显示覆盖日期/记录情况，不承诺无法证明的完整性；未来日期单列提醒，不混入“截至今天”的已发生数据。
- 月份归属与付款日期保持区分；流水总额与结算实收分别展示，不能相加。
- 微信用短段落或列表，不用宽表；长明细由用户继续展开或使用真实附件。网页/Markdown使用同一份报表数据，不能让不同渠道各算一遍。
- 原始JSON、英文字段、接口名、请求编号和服务器路径不进入主报表。只有附件实际发送或链接可访问时才说“文件已交付”。

## 截图数字的示意

以下仅用截图数字说明排版，没有读取用户账本，也未验证这些金额或日期范围：

> 已记收支概览
>
> 营业收入：35,842.00元
>
> 采购付款：2,135.00元
>
> 费用付款：44,270.00元
>
> 收支差额：−10,563.00元
>
> 已记支出高于收入10,563.00元。此差额不等于利润。
>
> 利润暂无法计算，还缺实际耗料成本、库存等核算依据。
>
> 统计时间和记录完整性仍待核对。截图含2026年10月26日，不能直接称为截至2026年10月25日的完整报表。

## iLink没有外部Agent时

推荐在内置worker收到消息后、调用结构化capture前增加可配置的整理步骤：

`iLink消息 → 整理/追问 → 保存固定结构化请求 → 校验入账 → 中文回执`

模型由部署者显式配置，不能默认读取其他项目密钥。首次整理结果必须先持久化，重试复用同一请求与消息编号，不能每次重新生成后重复入账。真正不清楚的字段通过微信追问；模型不可用时保留原话并明确待处理，不把规则猜测冒充Agent理解。需要设计对话状态、失败重试和完成后的关联，不能只在worker中插入一次模型调用就宣布完成。

当前内置worker仍为受控规则入口，未实现上述整理层或待处理状态流程。外部Agent已拥有iLink时则由其整理，保持内置worker关闭；同一Bot账号只由一端拉取。

## 后续实现验收

固定报表模块应验证：空账本、已知零与未知值、跨月费用、重复日总额与明细、缺销售金额、未来日期、非默认金额口径、权限隔离，以及微信/Markdown数值一致。只在临时账本验收，不向用户账本灌测试记录。

内置iLink整理层应使用fake模型与fake通道验证：原文逐字保存、语义明确直接提取、缺失字段追问、模型超时、不重生成导致幂等冲突、提交后回复失败重试不双写，以及与现有游标/状态恢复一致。真实模型费用、账号与服务器联调另行明确配置。

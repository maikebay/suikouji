# 开发与测试经验

## 2026-10-23 分层记录模型

本次查阅了原工作区经验库的“多轮与副作用”“测试与验收”规则。以下证据来自本项目源码、实际 Python 命令输出与测试；不代表微信、网页或云端验收。

### 未识别数字不能默认解释为金额

- 失败证据：分层入口最初实测 `气温28度` → expense 28；`2026-10-20客流120人` → expense 2026 / 10 / 20；`评分-1分` → expense 1。
- 原因：旧 find_amounts 接受无金额单位的数字；日期只认中文月日；观测遮蔽只能保护已经识别的片段。
- 处理：先遮蔽观测，识别 ISO 日期，分层入口要求金额单位或明确记账关键词。否定、条件、疑问样例保留原话等待识别。
- 复测：`test_unknown_numbers_and_nonassertions_do_not_become_expenses`、`test_iso_date_is_not_money` 通过。确定性规则不能覆盖任意自然语言。

### 回填须按已存账目，不重解析重复原话

- 同一句原话拆为两笔 entry 后，每行都保留完整 raw_text。若按每条原话全量重解析，两笔账会被投影两遍。
- 本次使用流水 ID 唯一来源和每笔已存字段产生观测。缺失原话不合成正文；历史销量单位未知就留空。
- `test_v1_upgrade_preserves_ledger_and_backfills_once` 验证真实 v1 结构 fixture、旧表结构/行内容保持、重复执行不变。是临时库迁移验收，不是真实业务数据迁移。

### 原话、投影、重试日期和来源关联必须分别明确

- 读代码和故障注入证明：若原话和投影同属一个外层事务，投影异常会一并丢掉原话；只沿重试当天解析会移动“昨天”，留下新旧两组观测。
- 处理：先持久化 pending 原话，再原子提交投影/状态；保存 parse_base_date；重试替换原话派生的非金额观测。ledger_refs 独立保存在 record，清空观测后仍能关联最初原话。
- 复测：故障回滚、pending 恢复、跨日重试、清空重建、修改/撤销同步测试通过。当前设计用于本地 SQLite，未声称完成分布式并发消费。

### 受控词表与单位不能只看字符串长得像

- 初版 aliases 未 JSON 解码时，`牛` 会命中 `'["牛肉"]'`，更新合并还会按单个字符拆开。
- 已统一按列表解码、精确别名匹配并拒绝别名冲突。人、桌、单分不同指标；汇总/趋势按单位分组。
- 评分看均值、天气看次数；通用 SUM 字段不等于每种指标都适合求和。单位别名只表达同义，数值换算仍需专门处理。

## 2026-10-23 补充、修正与待核对

### 修正要写回原行，而且自己也要有来源

- 老板事后补一句数量、改一个金额：新增一笔就重复入账，直接覆盖原行旧值就没了。做法是改原行 + 一条 `source='review'` 的原话，用新增列 `correction_of`（改的是哪一行）和 `correction_detail`（before/after/最初原话ID）留档，`dedup_ref='review:<request_id>'` 保证同一次改动只生效一次。
- 不要把修正信息塞进 `record.ledger_refs`。那个字段的语义是「这行账目由哪条原话产生」，一旦修正原话也写进去，`record_for_origin` 在观测被清空重建时可能把账目认到修正原话上，来源就错了。修正原话用 `correction_of` 指回去，被改行的来源仍指向最初原话。
- Schema 3→4 只增两列加一个索引；旧库 `ALTER TABLE` 补列，索引建在迁移块里（不能写进 `_SCHEMA`，否则旧库缺列时 `CREATE INDEX` 会先失败）。

### 幂等要覆盖「同号不同内容」

- 只按 request_id 查重不够：第二次带着不同字段也必须不改。先 `record_find` 再写；并发同号由唯一索引挡下，捕获 `IntegrityError` 后按重复返回。
- 故障注入实测：`project_ledger_row` 抛错时 SAVEPOINT 回滚能同时撤掉原话和字段更新，不留半条修正（`test_failed_projection_leaves_no_half_correction`）。

### 商品改名不能留下旧商品的ID

- `update_sale` 改商品名：别名能归一就归一到规范商品；改成商品库里没有的名字时必须把 `product_id` 清空。否则这行销量挂着旧商品ID，`sales_by_product` 与标准成本会按旧商品的配方算它的成本（`test_unknown_product_name_drops_the_old_product_link`）。

### 紧贴销量的金额是这笔的合计，不是另一笔支出

- 失败证据：`牛肉面卖了30份300元` 原先记成一笔 300 元「其他支出」加一条金额待补充的销量。在网页上按待核对提示补上金额后，300 元就被算了两次 —— 这正是本轮要防的重复入账，而且从账面上看不出来。
- 处理：销量匹配后紧贴的金额（允许一个逗号/顿号，允许「共/一共/总共/合计」）算这笔销量的合计；中间隔着别的字就不认领（`牛肉面卖了30份，买了牛肉300元` 仍是一笔进货）；只有写明「一份/每份/单价」时后面的数才是单价，这条与改动前一致。`_SALE_RE_B` 的商品名不再吞掉尾随金额（`卖了30份牛肉面300元` 不再得到商品名「牛肉面300元」）。
- 复测：`test_sale_total_is_not_a_second_expense`、`test_amount_after_other_words_still_belongs_to_the_expense`；原有 163 项全量通过，`test_sales_detected`（一份12块→360）行为未变。


### 独立审计补出的边界（2026-10-24 复测）

- 销量正则不能把“紧贴金额”当成一个单一写法：合计词要覆盖 `总计/共计/拢共`，允许“是”和中文数字；金额后面若紧跟 `成本/房租/买菜/买了` 等支出或进货词，则金额属于后一句，销量保持待补。单价只在“每份/一份/单价”等明确标记下计算；裸“卖300元”是整笔合计。数量在前的“卖了30份牛肉面，一份12块”也必须与商品在前的语序一致。
- 识别销量时只能遮掉实际匹配的 span，不能把同一空格分句的前缀全遮掉：`今天营业额1280 牛肉面卖了30份300元` 要同时保留总额和销量；商品名中粘着的 `300 元/三百元` 要截成金额，不得创建“牛肉面300”这类假商品。
- 修正留档要取真正写回库里的值。商品名按别名归一时，`after` 是规范名，`product_id/product_category` 的顺带变化也进 `side_effects`；否则历史第一条 after 和下一条 before 会断链。相同 request_id 的原样重试要先查重再比较字段，返回 `duplicate`。
- 输入边界在后端兜底：`entry.amount`、`sale.qty` 不能清空；拒绝布尔、NaN/Infinity、超大整数，避免 SQLite 完整性错误或 `float()` 溢出被误报成 500。深层 JSON 的 `RecursionError` 统一返回 JSON 400。网页历史从按行 corrections 取，不能依赖只保留 100 条的原话列表。
- pending 原话续跑先用条件更新认领为 `parsing`，认领不到就返回 duplicate；否则两个连接都可能把同一个 request_id 投影成两套 entry/sale。所有修正和投影仍在 SAVEPOINT 内，失败时原话、账目、观测一起回滚。
- 复测：`python3 -m unittest discover -s tests` 为 172 项通过；新增回归覆盖合计同义词、支出尾随、数量在前单价、前缀总额、别名副作用、原样重试、非法数字和深层 JSON。2026-10-24 追加的回归还覆盖无空格营业额前缀、采购后紧接销量的 span 归属，以及相邻金额不被中文小数识别吞并。
- 这次172项复测时尚未承诺无标点连续销量和无分隔同类费用；两者由下面的独立续轮处理。旧 `parser.js` 与 Python 解析器一致性仍不在范围内。当前网页服务路径由 `engine/parser.py` 提供。

## 2026-10-24 连续销量与无分隔费用

### 先建立红灯，而不是加一条更贪心的正则

- 确定性最小复现：`卖了30份牛肉面卖了20份炒饭` 只得到牛肉面20份；`房租8000水电200` 两笔都算房租；`牛肉面卖了30份共300元买了牛肉680` 把300和680都记成采购，销量缺金额。三条断言最初退出1。专门边界测试首次11项出现14个失败断言（含subtest）；后加标点变形和HTTP测试。
- 根因是两个全局商品在前/数量在前正则交叉吞句，错误候选先占span；费用只看rank变化，同为expense的水电/人工不切；分段内所有金额又被同一个分类复制。不是增加商品词典就能解决。
- 修复为从左到右定位唯一销量锚点，再认本笔商品和金额；费用按独立分类/交易锚点分段。旧A/B正则及重试匹配器已删除，避免两套规则漂移。

### 金额认领与不确定性必须一起验收

- `共/合计/总计` 明确认领销量合计，即使随后另有采购。裸 `300元交房租8000` 则只记8000，300留leftovers；不能让销量和费用抢同一金额，也不能复制为第二笔房租。
- 复核又发现单一锚点后多金额会静默多记：`交房租300元8000`、`交房租8000前300元`。已固定为每段最多一个金额，其余未识别；后置类别仅绑定紧邻金额，`营业额1280元300元成本` 不能让成本覆盖1280。
- `leftovers` 要在已经成功写下其他行时也向上传递，否则原话错误标parsed。HTTP回归检查partial持久化；原地补销量金额后条数/来源不变，同号换正文重试不重写；一般未识别片段不自动进入缺字段待核对清单。
- `卖了30份牛肉面炒饭卖了20份` 没有商品分界，不猜长商品或词典拆分。整段留待识别；加入逗号/日期/平台边界才拆。缺商品的销量不把数量变金额，且标点后的完整销量可独立恢复。

### 等长遮蔽仍可能丢失语义作用域

- 数量单位会与类别首字碰撞：`水电200人工600` 的200人、`房租8000包装80` 的8000包曾被遮蔽。人排除人工/人手，数量单位与完整账目关键词重叠时完整词优先；采购「三箱/三包」继续保留。Arabic/Chinese都加回归，不能只补单一数字写法。
- 金额正则中尾部可选单位前的空白原来会吞掉已遮蔽日期：8000的end越过「今天」，日期被切到前一笔。空白改成只与真实单位一起匹配。
- 日期/平台不是商品名；ISO、月日、日号与连续日期加回归。销量遮蔽后要保留日期的后续作用域，否则「昨天销量…今天销量…房租8000」仍把房租记到昨天；日期按原位恢复并顺序分段。
- 数量在前的「合计是/总计是」还可能粘进商品名；显式标记的商品尾界与金额读取必须使用一致语义。

### 验证与实际范围

- 复核继续锁定数量在前的「每份卖/单价是」与后置平台信息；商品尾界必须和金额读取使用相同标记语义，平台维度从本笔完整span读取。额外合计（包括单价后合计）只作未识别，不兜底成其他支出；日期继承从base开始，不让后文「昨天」回溯改变前文未标日期的费用。
- 最后一轮独立探针发现数量在前的小数/万单位/千位逗号只截取数字尾巴，导致商品名污染或销量落成revenue；5条subtest先红，金额token改为完整读取小数/千位分组并保留原位索引后转绿，没有把原文压缩后再推span。
- 只读工作流阶段有意与主线程实施并行，部分报告读取的是修改前快照；不把旧输出当最终缺陷。每条采纳的报告都在主线程先独立红灯、修复再绿灯。最终销量reader当前快照未留下已确认的支持语法缺陷；这不是任意语法无缺陷保证。
- 完整临时库测试203项通过（最终复测1.635s），以[项目验证摘要](../../README.md)记录的复核范围为准。新增专门边界测试、HTTP、SQLite来源/观测、汇总500元销售+8200费用、同号换正文、partial后原行修正，均走真实生产入口。

### 迟到复核：月份在金额前，日历错误不能回退

- 先增加4项专门边界测试和2项真实HTTP测试，红灯覆盖48种月份语序/标点组合、非法日期、合法闰日、原话持久化及同号换正文重试。月份根因是只到分类处才切，第一段残留两个归属月而被整体丢弃；现仅在前后两侧都有独立分类与金额时，先按后一个归属月起点切分，付款日与归属月仍分开，不因采购数量另拆一笔。

- 严格校验不能让来源在保存前丢失。`observe._date_at`只在原话预存元数据阶段跳过非法日期，原话先落库；之后投影事务内的`parse`统一抛错并回滚，事务外将原话标`rejected`。同号换正文也拒绝，不留下账目、销量或经营观测；这不是吞错后按今天入账。
- 日期相关辅助函数必须显式传递同一解析基准：`_dates/_ledger_amounts/_entry_boundary`、商品名和付款尾界、噪声判定都沿用base。否则原话保存的2024闰年在辅助分析时又按机器2026年判断，合法`2月29日`也会失败；显式2024年与基准2024年均已回归。

## 2026-10-25 Agent 与 iLink staging 的恢复边界

- 业务去重不等于响应幂等。旧流程在业务提交后才保存 Agent 响应：中断后重试，capture 丢 `parsed`、修正丢 `changed/history`、导入变成 `imported=0`。现在 claim、业务、完整响应同属外层事务；重试只改顶层 duplicate。真实子进程 `os._exit` 在认领后、finish 前、finish 后但提交前、提交后退出，覆盖正常 capture、拒绝输入、非餐饮确认、修正与导入；临时库重开检查完整回滚或完整重放。
- 原话先保存的 legacy ingest 约定保持；Agent 事务内确定性拒绝会保存 rejected 原话和终态响应。基础设施失败则整体回滚，调用者用原编号重试。pending/parsing 不缓存为完成。旧版本已有业务但缺响应的孤立请求返回 `recovery_needs_review`，不能凭缩减的 duplicate 结果宣称精确恢复。
- SAVEPOINT 最外层 RELEASE 可能因读锁或磁盘错误失败，并留下连接仍在事务内。临时双连接读锁测试先复现，现失败显式 rollback，避免下一请求带入旧业务。非法 profile 创建工作空间也放入事务，防止后续无关提交持久化孤立 shop。
- 独立调用 claim 的 INSERT 唯一约束失败也会开启隐式事务；若直接返回，后续服务 savepoint 的 RELEASE 不会真正提交。新增九种 claim 状态/业务组合，先复现成功回包后另一只读连接看不到结果，再用 claim 自有 savepoint 修复，保留外层回滚。principal/request 不能用冒号拼接作身份，现用 JSON tuple 哈希；旧完整缓存保持，旧业务无缓存即使 claim 已释放也拒绝缩减重放。修正先重放已授权工作空间内的完成缓存，目标删除不影响旧响应；capture 显式指定的 profile 后续改变也不阻止完成缓存重放。新写入仍查当前 profile 与目标归属。
- 导入预览绑定 principal/workspace/CSV SHA-256，1800 秒有效，成功提交时和响应一起消费到一个 request_id；原请求成功缓存可在过期后重放。预览保存已有批次 ID；缺响应且批次在预览后才出现时，无法区分旧 orphan 与另一提交，安全地要求核对和重新预览。重新预览已有批次仍允许确认重复文件，不改 legacy importer 语义。迁移、消费回滚和备份恢复都有临时库测试；无外部 ID 的同身份流水改金额返回冲突，不能静默多记一笔。
- 状态文件先成功写盘后更新内存，并先持久绑定 account。已有 cursor/token 但缺账号的旧状态拒绝自动归属。固定 `.tmp` 跟随符号链接覆盖假账号的离线反例已复现；现在随机排他创建 0600 临时文件，fsync 后原子替换并同步目录。仍仅支持一个状态写者，没有多进程文件锁。
- transport 超时兼容空批次要有明确标记，不能刷新真实成功轮询心跳。发送旧 context token 的 -14 按协议只做一次无 token 回退；成功继续，轮询/回退仍过期才停止并失去就绪。Bot 发送失败或 cursor flush 失败重放不重复入账，回复仍是至少一次语义，没有 durable outbound outbox。
- readiness 不能只看 schema_version=5，也不能只选几列：缺 product.category、sale.unit、entry.external_id 或 entry.date 曾误报 ready，并可能在请求时自动补列或 500。HTTP 与 runtime 共用全部运行表/字段的只读检查；逐列重命名临时库中的当前字段，验证 503 且文件字节不变，不让请求承担迁移。runtime 仅显式启用才加载账号；Bot SQLite 在所属线程创建和关闭，API/Bot 用进程内锁串行写入，长轮询不持锁。所有验证使用内存/TemporaryDirectory、假账号和假客户端；真实 iLink、扫码、服务器和多进程并发尚未验收。

# Agent 能力契约

Agent 在处理用户原话前，先带 Bearer key 读取 `GET /v1/capabilities`，了解产品当前支持、规划中和明确不支持的能力。接口合同见 [OpenAPI](openapi.yaml)。本地 demo 的 `/api/capabilities` 继续兼容；它不提供 staging 接入所需的认证边界。

## 先由 Agent 整理口语，再调用工具

用户口语可能混杂多个事件、语气词、跳跃叙述、遗漏字段或不确定推测。调用方 Agent 负责理解并整理，随口记负责结构校验、数据归属、持久化和防重复。不要要求用户先把自然表达改成固定记账句式。

`/v1/capabilities` 的 `agent_policy.input_preparation` 会声明这个分工，并直接返回 `structured_schema` 和 `request_example`，含必填字段、允许值和业务约束；示例工作空间和消息编号应替换成当前已授权的实际值。推荐调用 `POST /v1/captures`，同时传入逐字原话 `text` 和 Agent 整理后的 `structured`；省略 `structured` 才沿用旧规则解析。显式传 `null` 或错误结构会报错，不会静默回退为原话解析。服务端不调用额外模型，没有新增模型供应商或 SDK 依赖。

Agent 整理时应当：

- 分开实际收入、采购、费用、单品销量、受控非金额观测和生意随想。定性客流和生意好坏按受控说法记入观测，不编客流人数、老客占比或金额。
- 账目、销量、观测按既有日期规则提交明确的 `YYYY-MM-DD`，每条附逐字 `source_quote` 和 `assertion: actual`。随想使用独立规则，不提供 `assertion`。服务端验证来源存在和结构合法，不能证明 Agent 的语义判断一定正确。
- 随想的 `date` 是归档日，默认收到原话在工作空间时区中的日期。收到“昨天想到下周推新品”仍归今天，昨天、下周留在正文；只有明确“这条随想记在昨天”才按指定日归档。首次接收时间和日期基准固定，跨午夜重试不得重算；非法或冲突归档日期先澄清，不替换为今天。
- 显式区分日营业总额与交易、流水总额与结算实收；缺少会改变金额含义的口径时追问，不能把两个口径相加。
- “大概做了1300”“花了两百多”“可能收入一千左右”不能变成精确1300、200或1000账目。可先保存其他明确内容，不确定金额原句留在 `leftovers`，回执说明未入账再追问。“今天的营业额很差，只有1300”金额明确，不因口语化重复追问。
- 新品、配方打算和经营感受作为普通随想保存，保留“可能”“觉得”“想试”的原意；不是已发生财务事实，也不创建 plan 子类型、任务、执行时间、截止时间或提醒。
- 将未能结构化或不支持的内容，以原文片段放入 `leftovers`；完整 `text` 和逐字来源不可改写，`thought.body` 可以整理。Markdown、链接或类似指令的内容仅保存，不触发抓取、执行或其他动作。

结构化数据保留四个必填数组：`entries`、`sales`、`observations`、`leftovers`，新增可选 `thoughts`。缺省随想仅在计算原始请求指纹后的验证副本中补 `[]`；显式 `null` 或其他非数组值拒绝。四个领域数组 `entries/sales/observations/thoughts` 合计最多50行，未解析片段另计最多50个，不能全部为空。纯随想仍要传四个旧数组的空数组。当前仍只允许餐饮 profile，纯随想也不绕过其他行业的确认边界；不能因为用户报了其他行业就自动选餐饮。

账目要求显式日期、类型、分类、金额、`amount_basis`、`granularity`、来源片段和实际发生声明。金额必须是非负有限 JSON 数值，不接受布尔值、数字字符串或超过1e12的值。收入分类为“营业额”、采购为“食材成本”；费用使用当前已支持的分类。采购数量与单位在明确时成对提供，不知道就省略，不编造；费用归属月与付款日分开。

销量要求明确商品、日期、数量、单位、口径、粒度及来源，未知金额用 `null`。非金额观测包括客流、订单、天气、排班、评价，以及餐饮定性说法。有明确人数或桌数时，客流仍用 `measure=人数/桌数` 和 `value_num`。没有数字的常见说法用文本标签，禁止补人数或金额：

| 原话示例 | kind | measure | value_text |
| --- | --- | --- | --- |
| 老顾客非常的多、老客多、回头客很多 | 客流 | 情况 | 老客多 |
| 人很多、客人多、客流很多 | 客流 | 情况 | 人多 |
| 客人少、人少、客流少、客人不多 | 客流 | 情况 | 客人少 |
| 客流一般、客人一般 | 客流 | 情况 | 客流一般 |
| 生意还可以、生意还行 | 生意 | 好坏 | 还可以 |
| 生意不错、生意很好 | 生意 | 好坏 | 不错 |
| 生意一般 | 生意 | 好坏 | 一般 |
| 生意不好、生意很差、生意有点差 | 生意 | 好坏 | 不好 |

`value_text` 用上表标签，`source_quote` 用原话连续片段。这些行不填 `value_num`，也不填单位。不能把「老客多」写成 30 人，不能把「生意还可以」写成金额或评分。「天气很好」不是受控天气，不要猜成晴；已支持的阴/晴/雨/多云/雪保持不变。不能手工提供营业额、进货金额等派生观测来绕过账表。账目和销量仍由业务表派生相应观测，财务汇总只计算业务表，不回加观测金额。

## 随想字段与标签

随想必填 `date`、非空 `body`（最多2000字符）和非空 `source_quote`（最多2000字符）；来源必须是原话中精确连续片段。`title` 可省略，提供时非空且最多80字符，不编造标题。`tags` 可省略，缺省 `[]`。长度按 Unicode 字符数计算，原话仍最多2000字符；`null`、未知字段、客户端 id/归属/时间戳、金额和任务字段均拒绝，不截断。文本必须能以 UTF-8 编码；随想标题、正文和来源不接受 U+0000。非法字符返回校验错误，不替换或删去后写入。

标签先做 Unicode NFC，去首尾空白，去至多一个开头 `#` 后再次去首尾空白；规范化后1～32字符，保留大小写，拒绝内部空白、控制字符和剩余 `#`。数组先检查最多20项，再按规范化后的精确值去重并保留首次顺序。没有标签照常记，不追问；Agent 可按明确主题提取少量标签，原生规则只提取明确 `#标签`。标签只属于随想，不自动关联同名采购账目，不提供别名、改名或分类树。

## 混合原话的调用示例

工作空间时区为 Asia/Shanghai，收到时间2026-10-26 20:00；已确定门店日营业总额与 gross 口径时，可提交：

```json
{
  "workspace_id": "shop-a",
  "request_id": "message-20261026-001",
  "source": "agent",
  "text": "今天营业额1300元，阴天，生意还可以，老顾客非常的多。记个想法：明天想用南瓜做甜品，可以搭配木薯、银耳、枸杞。#新品 #南瓜",
  "received_at": "2026-10-26T20:00:00+08:00",
  "structured": {
    "entries": [{
      "date": "2026-10-26",
      "type": "revenue",
      "category": "营业额",
      "amount": 1300,
      "amount_basis": "gross",
      "granularity": "daily",
      "assertion": "actual",
      "source_quote": "今天营业额1300元"
    }],
    "sales": [],
    "observations": [{
      "date": "2026-10-26",
      "kind": "天气",
      "measure": "天气",
      "value_text": "阴",
      "assertion": "actual",
      "source_quote": "阴天"
    }, {
      "date": "2026-10-26",
      "kind": "生意",
      "measure": "好坏",
      "value_text": "还可以",
      "assertion": "actual",
      "source_quote": "生意还可以"
    }, {
      "date": "2026-10-26",
      "kind": "客流",
      "measure": "情况",
      "value_text": "老客多",
      "assertion": "actual",
      "source_quote": "老顾客非常的多"
    }],
    "thoughts": [{
      "date": "2026-10-26",
      "title": "南瓜甜品试做想法",
      "body": "明天想用南瓜做甜品，可以搭配木薯、银耳、枸杞。",
      "tags": ["新品", "南瓜"],
      "source_quote": "明天想用南瓜做甜品，可以搭配木薯、银耳、枸杞。#新品 #南瓜"

  }

```

工具按整理结果写入一笔1300日营业额、阴天、生意还可以、老客多和随想，不再运行原话规则生成第二套投影。随想和定性观测不改变1300汇总；账目派生观测也不回加。原话、商品、账目、销量、观测、随想、标签、请求认领和完整回执同事务提交或回滚，一条非法随想就拒绝整个 structured 请求。新结构化解析版本为 `agent-structured-2`，不重标历史记录。

## 微信 iLink 入口

推荐让已经接入 iLink 的外部 Agent 负责单聊文本收发：微信消息 → Agent读取能力并整理 → 同一次 `POST /v1/captures` 提交原话和 `structured` → 依据真实回执回复微信。iLink只是消息通道，不负责理解杂乱口语。

- 若 Grokbot 已经收发 iLink 消息，随口记只开认证 API，自带 iLink worker 保持关闭。同一 Bot 账号只允许一端拉取消息和维护游标。
- 发送请求的稳定身份应包含 Bot账号、peer、message_id，可将该元组作无歧义JSON编码后哈希，作为100字以内的 `request_id`；来源设为 `ilink`。不要仅按文字内容生成编号，同样的话可能是两次合法记录。
- Agent首次整理后先持久保存要发送的完整请求，再调用工具；网络重试重用完全相同的原话、整理结果、时间和请求号。重新让模型整理导致结果变化时，同号会返回409，而不能换号绕过去重复写账。
- 需要追问时，由 Agent 负责保存对话上下文和处理回答；可先保存明确随想、受控观测或其他明确账目，把不确定部分留作未解析。当前 API 没有将简短“对”“直接记”绑定旧 partial 并补写的接口，也没有完整对话状态机或自动历史补录。
- 数据和回执持久化成功后再按通道策略确认消息和推进游标；回复失败不意味着入账失败，重试先查原回执，不重复入账。

随口记自带的 `channel.bot.ILinkBotWorker` 是“iLink文本 → AgentService受控规则入口 → 短回执”，没有模型调用。共享文本入口有限支持“记个想法：”“记个随想：”和“明天想试…”“下周想推新品…”；具体正反例见[解析边界](parser-boundaries.md)。它不承担自动欢迎、查询对话或多轮确认；查询由外部 Agent 调用公开 API。原生入口不支持指定另一个随想归档日，识别到这类指令应保留并说明需要 Agent，不能默认为今天。单独启用 worker 不会获得任意口语理解；不要同时启用两端收消息。

## 随想查询与原话时间线

先确认当前工作空间及能力项 `thought.capture`、`thought.list` 为 `available`，读取 operations 中实际提供的路由。用户要“这个月的新品随想”时调用 `GET /v1/thoughts`：

| 参数 | 约定 |
| --- | --- |
| `workspace_id` | 必填，只能访问认证主体有权访问的工作空间 |
| `start/end` | 可选，严格有效 `YYYY-MM-DD`，按随想归档日闭区间过滤，反向范围拒绝 |
| `tag` | 可重复，如 `tag=新品&tag=南瓜`；规范化规则同写入，AND，最多20项后去重，不拆逗号 |
| `q` | 最多200字符，标题/正文 Unicode casefold 后字面子串搜索，不执行正则；标签使用 tag |
| `page_size` | 整数1～100，默认30 |
| `before` | 原样复用不透明游标，绑定工作空间及规范化日期、标签、关键词；翻页可改页大小 |

返回 `items/has_more/next_before`，按 `date DESC, created_at DESC, id DESC` 排序；空查询是成功的空列表。`next_before` 末页为 `null`。换工作空间或筛选需重新查询，不能拼装游标。非 tag 参数重复、未知参数或非法日期/标签/关键词/页大小/游标返回400；显式空 start/end/tag/before 同样拒绝，空 q 表示不限制。展示日期、可读标题或正文、标签；未取完应说“还有更多”，不能声称全部。查询前例如“正在查看糖水铺最近30天的新品随想”。

`GET /v1/timeline` 仍是一条原话一个条目；`types` 仅可省略或单值 `thought`，后者筛选含随想的原话，混合原话仍含账目预览。它沿用 capture 事件时间和旧分页游标，日期含义不同于随想列表。将上一页 `next_before` 三项以 `|` 连接后原样回传；空值、重复、缺段、多段或日期/时间无效均返回 `400 invalid_cursor`。`projection_counts.thoughts` 是总数；`thought_preview` 最多3条、每条正文最多120字符，完整内容需随想列表或 `GET /v1/captures/{id}`。时间线关键词纳入随想标题、正文及标签。有原有领域行时沿用这些行的事件日期算法，纯随想才取记录日最大值，正文的未来时间不改变财务事件时间。

随想与标签在同一本数据库的独立 `thoughts/thought_tags` 中保存，经 `capture_id` 关联原话。要查南瓜进货仍使用账目查询，不能宣称同标签已关联账目；没有独立随想创建、编辑、删除或撤销接口。

## 面向用户的进度和报表

`agent_policy.user_presentation` 要求调用方把接口术语翻译成业务内容。查询前说明实际选定的账本、时间和范围，例如：“正在整理糖水铺10月的营业收入、进货支出和各项费用，并核对各商品销量。”范围还没确定就先明确范围，不把 `entries / sales / summary` 当进度说明，不声称尚未执行的查询已完成。

报表按“账本与统计时间 → 收支概览 → 主要支出 → 商品销售 → 待补充信息”组织，只展示有依据的数据：

- 金额用人民币、千位分隔和两位小数；收入、采购付款、费用付款分别列出。
- 收支差额是已记收入减采购付款及费用付款，不等于利润；采购付款不等于实际耗料成本。
- 未知值写“暂无法计算”并说明缺什么，不能输出 `None` / `null` 或当作0。未记录日期不算零营业，未取完的分页不能声称完整。
- 每份报表注明统计时间、金额口径和记录覆盖情况。日总额、单品明细和派生观测不重复相加；不能把多月数据当作一个月结果。
- 微信默认发简短纯文本，先给核心数值，长明细另行展开；网页或文件可以用表格。调试字段、接口路径、拉取次数和服务器文件路径不进入主报表。
- 文件只有通过通道发送附件或提供真实可访问的链接后，才能称为已交付；`/workspace/...` 不是用户的下载地址。

固定报表和内置iLink整理层的具体产品方案见[用户可读回复与固定报表方案](report-output-design.md)。本版本提供上述机器可读展示约定，API仍返回业务JSON；它不能强制任意外部Agent遵守模板。要在产品层固定输出，需要另行实现由产品计算数据并渲染的报表接口/模板，Agent仅选择时间范围与补充解释。当前没有这类新报表生成接口，也未把iLink内置worker改成报表机器人。

## 写入结果应怎样向用户说明

`POST /v1/captures` 返回 HTTP 200，表示原话得到一个终态处理结果；是否入账必须查看响应中的 `entries` / `sales`，不能从 HTTP 状态码或 `observations` 推断。机器可读约定见 `/v1/capabilities` 的 `agent_policy.capture_result_policy`。

- 原话保存：查看 `capture`，保留用户逐字原文。新结构化回执的 `normalization.thoughts` 回传经校验的随想，顶层 `thoughts` 返回已保存行；原话详情也含完整正文与标签。历史完整缓存可能没有 `thoughts`，继续原样重放，客户端须兼容缺省，不推断旧记录已被重解析。
- 财务与销量：只报告实际返回的 `entries` / `sales`。天气等 `observations` 或随想保存成功，不等于营业额已入账。
- 未解析内容：查看 `parsed.leftovers`。新回执还有 `coverage`：`business_points_saved` 表示账目、销量、观测或随想里至少有一条已记下；`has_unstructured_fragments` 表示还有未结构化原话。两者都为真时，`partial` 只说明杂句还没结构化，经营要点已经记下，不要说成整单失败。先说明已保存的账目、观测或随想，再点出未结构化原话；只有原话里的金额才说未入账。定性观测没有人数或金额，不能加进汇总。无未解析片段且有投影才为 `parsed`，纯随想也可成功。
- 网络失败或结果未知时说“暂时没拿到结果，正在核对”，按原编号和原完整请求重试以取回回执；回复发送失败不等于写入失败，不能换号重发整段原话，也不能无依据声称已存草稿。
- 用户确实没有说明金额归属时才追问；“今天的营业额很差，只有1300”已经表达营业额1300，旧规则漏识别属于解析能力缺口。
- 不要把“Agent整理”实现成改写原话后用新请求号再提交文本。正确做法是在同一次 capture 中保留原话并附 `structured`。

混合成功可说：“今天营业额1300元和阴天已记下，南瓜甜品的想法也保存了。”近似金额的部分成功可说：“南瓜甜品的打算和今天的经营感受已记下。‘大概做了1300’还没作为营业额入账，需要确认准确金额和含义。”只存随想时可说：“新品随想已记下。”不需要为无标签追加问题。

## 安装后介绍与冷启动

连接完成后先验证认证、已有工作空间和实际行业能力；已配置的店名和 profile 不重复问。确实缺少时最多问一两句账本称呼或主要生意，通过真实可用的部署/配置流程持久化；没有写入接口不能回复“已改名”。用户对话中的称呼不等于系统配置已更新，也不需要先配置常用标签。

仅在能力接口确认随想录入与查询可用后，外部 Agent 可使用以下介绍，并替换为已有账本名称：

> 我是随口记，帮你用说话或打字记生意账，也把新品灵感和经营随想留在一起。忙时可以记进货、开支和营业收入；想到新口味也随手记下，以后按时间或标签找回来。比如：“今天进了20斤南瓜80元”“记个想法：下周试芋圆新品 #新品”。想回看就说“这个月的新品随想”。金额或日期确实不清楚时，我会再问一句。糖水铺这边，先说一笔试试。

原生 iLink worker 不自动发送此欢迎词或处理查询对话。介绍不承诺库存/剩料核算、任务提醒、随想编辑、任意改名、标签别名或固定报表；错账可调用 `ledger.void`（`POST /v1/entries/{id}/void`）软作废并保留审计，不物理删除；按能力接口的实际状态调整。

## 账目作废（软作废）

能力项 `ledger.void` 为 `available` 时，外部 Agent 可在用户确认后调用：

`POST /v1/entries/{entry_id}/void`

```json
{
  "workspace_id": "shop-a",
  "request_id": "void-20261029-001",
  "reason": "语音听写成马清粉，与正确马蹄粉重复"
}
```

- Bearer 认证；工作空间必须属于当前主体。目标账目不存在或不属于该工作空间返回 `404 entry_not_found`。
- 软作废：保留原行，写入 `voided_at` / `void_reason` / `voided_by` 与 `entry_void_audit` 审计；不物理删除。
- 已作废再调用仍返回 200，`already_voided=true`；同 `request_id` 重放则 `duplicate=true`。
- 默认 `GET /v1/entries`、`/v1/summary`、报表与 timeline 账目预览不再计入已作废行；`GET /v1/captures/{id}` 详情仍可见并带作废字段。
- 金额纠错优先用修正接口；作废用于整笔错误或重复入账。

## 必须遵守

- 能力状态为 `available` 才能直接使用；`planned` 只能向用户说明尚未实现，不能伪装成已执行；`unsupported` 必须明确告知边界。
- 工作空间、行业 profile 或会影响入账的实际/预算、日期、金额归属和口径不明确时先澄清；正文有“想试”“明天”不阻止作为随想保存。
- “新品售价30元”“预计花300元”“以后可能采购100斤”不能仅凭数字直接记成正式账。
- 个人微信、客如云和外卖平台直连当前都不能承诺已支持。
- 标准成本只能标为估算，不得称为实际耗料成本或实际利润。
- 当前原生 iLink worker、CLI和本地网页仍可走受控规则入口；它们本身没有模型来整理任意口语。Agent先整理的路径需由外部 Agent 显式调用带 `structured` 的API。

## 当前基础

schema v8（自 v7 起含自定义字段，v8 增加账目软作废字段与审计表）在 v6 基础上保留 `record` 原话、`entry`/`sale`/`observation` 投影和旧 `shop_id` 兼容，新增独立 `thoughts` 和可索引 `thought_tags`；随想经自己的 `capture_id` 关联来源，不向 `ledger_refs` 塞入 `thought:`。公开字段使用 `workspace_id`。profile 作为工作空间元数据和模块边界，REST 和 iLink Bot 共用 `AgentService`，工作空间必须属于服务端配置的 owner。

## 写入与重试

- `request_id` 是业务幂等键，限定在 principal、workspace 和 operation 下；同号不同内容返回 `409 idempotency_conflict`。服务端生成的 `X-Request-ID` 只作请求追踪，不能代替业务编号。
- capture、修正和导入的业务写入与完整响应在同一事务提交。相同请求重试保留原响应的内容，只把顶层 `duplicate` 设为 `true`；导入内层的 `imported` 仍表示原请求导入的行数。工作空间仍须属于当前 owner；行业 profile 后续变更或修正目标后续删除，不阻止已完成请求重放，新的写入仍校验当前 profile 和目标归属。
- 文本模式与结构化模式共用 capture 幂等域。同编号改模式、原话、随想正文或标签都冲突；缺省 `thoughts` 和显式 `[]` 也是不同原始请求，不能为重试补字段。默认标签、标签规范化和默认随想数组仅用于验证副本，不能先改正文再计算指纹。旧四数组请求和旧文本请求的完整缓存继续兼容，只沿用顶层 `duplicate` 的重放变化；不补历史 `thoughts`，不自动重解析。
- `/healthz` 不访问数据库；`/readyz` 只读检查完整性、版本、必需表与字段，以及配置的工作空间和 worker 心跳。未初始化或缺少控制表的数据库返回 503，API 请求不会替它建表。升级/初始化需在服务停止后显式执行。
- `pending` / `parsing` 不能视为完成，返回 `409 request_in_progress` 后应使用原业务编号稍后重试。`rejected` 表示原话已保留、没有写入账目，修改原话后需要新编号。非法结构化输入在写库前报 `400 invalid_structured`，不会回退运行旧解析器。
- 旧版本如果留下“业务已提交、响应未保存”的请求，无法保证重建首次完整响应；对可识别的旧原话、修正和导入返回 `409 recovery_needs_review`，保留数据供人工核对，不重新写账或静默缓存缩减结果。即使旧认领已释放，也检查业务证据；已完成的旧请求仍重放完整缓存。仅认领后退出、尚未写入业务的旧请求可在租期过后重试。新原话和修正使用无歧义的 principal/request 编码，避免含冒号的不同组合共享业务身份。
- CSV 先调用 `/v1/imports/preview` 展示精确预览，再明确确认并调用 `/v1/imports/commit`。预览绑定 principal、workspace 和 CSV 的 SHA-256，有效期1800秒，成功提交时绑定一个 request_id。过期或消费后的 token 不能用于新的提交；原提交的相同请求仍可重放缓存响应。预览同时记录当时已有的同文件批次，并用 `duplicate_file` 和 `existing_batch`（编号、文件名、行数）展示。预览之后才出现批次但本请求没有完整响应时返回 `409 recovery_needs_review`，核对后需重新预览；旧预览没有批次快照且文件已导入时也适用。CSV 的在线上限是 32768 字节 JSON 请求，服务层另限 2MiB，不能使用 XLSX 上传上限。
- XLSX 使用 `POST /v1/imports/xlsx-preview` 上传，再由 `POST /v1/imports/xlsx-commit` 确认提交。文件最多 10MiB，表单元数据最多 64KiB，实测解压最多 50MiB、1000 个成员。预览绑定原件摘要、工作簿中的稳定工作表编号、表头、映射和字段配置版本；不执行宏、公式或外链。公式只保留缓存值并标为未核对。
- 信息不足或能力不支持时先追问。Bot 当前只做单聊文本 capture；任务提醒、平台直连、普通个人微信和媒体处理不能被当成已完成能力。

已保存的旧 `partial` 不会因升级自动补账。先读取原回执和该日账目，再取得可独立解释的真实确认原话，例如“确认10月26日营业额1300元”，才以新 capture 记录这条新原话。简短“对”“直接记”不能自动绑定并补写旧 capture；不能伪造合并原话，也不声称建立跨 capture 关联。当前修正接口只能修改已有业务行，不能给只有观测或随想的旧原话增加账目。禁止换新请求编号重发整段混合原话修复历史记录。

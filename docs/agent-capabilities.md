# Agent 能力契约

Agent 在处理用户原话前，先带 Bearer key 读取 `GET /v1/capabilities`，了解产品当前支持、规划中和明确不支持的能力。接口合同见 [OpenAPI](openapi.yaml)。本地 demo 的 `/api/capabilities` 继续兼容；它不提供 staging 接入所需的认证边界。

## 先由 Agent 整理口语，再调用工具

用户口语可能混杂多个事件、语气词、跳跃叙述、遗漏字段或不确定推测。调用方 Agent 负责理解并整理，随口记负责结构校验、数据归属、持久化和防重复。不要要求用户先把自然表达改成固定记账句式。

`/v1/capabilities` 的 `agent_policy.input_preparation` 会声明这个分工，并直接返回 `structured_schema` 和 `request_example`，含必填字段、允许值和业务约束；示例工作空间和消息编号应替换成当前已授权的实际值。推荐调用 `POST /v1/captures`，同时传入逐字原话 `text` 和 Agent 整理后的 `structured`；省略 `structured` 才沿用旧规则解析。显式传 `null` 或错误结构会报错，不会静默回退为原话解析。服务端不调用额外模型，没有新增模型供应商或 SDK 依赖。

Agent 整理时应当：

- 分开实际收入、采购、费用、单品销量和非金额观测，不把天气、客流或经营评价当金额。
- 按工作空间与收到原话的时间理解“今天／昨天”，提交明确的 `YYYY-MM-DD`。不确定的日期先问，不能把非法日期改成今天。
- 每条事实附上逐字来源片段 `source_quote` 和 `assertion: actual`。服务端验证片段存在、字段合法，不能证明模型的语义判断一定正确。
- 显式区分日营业总额与交易、流水总额与结算实收；缺少会改变金额含义的口径时追问，不能把两个口径相加。
- 不把预计、计划、报价、否定、问题或“可能影响”的因果推测变成已发生账目。真正缺失或冲突时提问；仅仅表达口语化不是必须追问的理由。
- 将未能结构化或不支持的内容，以原文片段放入 `leftovers`；完整原话始终保存，不能替换为 Agent 改写的摘要。

结构化数据包含四个必填数组：`entries`、`sales`、`observations`、`leftovers`。三个领域数组合计最多50行，未解析片段最多50个；不能全部为空。当前仍只允许餐饮 profile，不借结构化写入绕过其他行业的确认边界。

账目要求显式日期、类型、分类、金额、`amount_basis`、`granularity`、来源片段和实际发生声明。金额必须是非负有限 JSON 数值，不接受布尔值、数字字符串或超过1e12的值。收入分类为“营业额”、采购为“食材成本”；费用使用当前已支持的分类。采购数量与单位在明确时成对提供，不知道就省略，不编造；费用归属月与付款日分开。

销量要求明确商品、日期、数量、单位、口径、粒度及来源，未知金额用 `null`。非金额观测仅限当前客流、订单、天气、排班和评价的受控指标；不能手工提供营业额、进货金额等派生观测来绕过账表。账目和销量仍由业务表派生相应观测，财务汇总只计算业务表，不回加观测金额。

## 截图原话的调用示例

用户说“今天的营业额很差，只有1300。阴天，马拉松可能影响生意。”，收到时间为2026-10-25，且当前已确定为门店的日营业总额时，可整理为：

```json
{
  "workspace_id": "shop-a",
  "request_id": "message-20261025-001",
  "text": "今天的营业额很差，只有1300。阴天，马拉松可能影响生意。",
  "received_at": "2026-10-25T20:00:00+08:00",
  "structured": {
    "entries": [{
      "date": "2026-10-25",
      "type": "revenue",
      "category": "营业额",
      "amount": 1300,
      "amount_basis": "gross",
      "granularity": "daily",
      "assertion": "actual",
      "source_quote": "今天的营业额很差，只有1300"
    }],
    "sales": [],
    "observations": [{
      "date": "2026-10-25",
      "kind": "天气",
      "measure": "天气",
      "value_text": "阴",
      "assertion": "actual",
      "source_quote": "阴天"
    }],
    "leftovers": ["马拉松可能影响生意"]
  }
}
```

工具按整理结果写入一笔1300日营业额和天气观测，不再运行原话财务解析生成第二套账目。“马拉松可能影响生意”保留原话，不当成已证实因果关系。收入、天气和未解析内容以及完整回执同事务提交；失败整体回滚。

## 微信 iLink 入口

推荐让已经接入 iLink 的外部 Agent 负责单聊文本收发：微信消息 → Agent读取能力并整理 → 同一次 `POST /v1/captures` 提交原话和 `structured` → 依据真实回执回复微信。iLink只是消息通道，不负责理解杂乱口语。

- 若 Grokbot 已经收发 iLink 消息，随口记只开认证 API，自带 iLink worker 保持关闭。同一 Bot 账号只允许一端拉取消息和维护游标。
- 发送请求的稳定身份应包含 Bot账号、peer、message_id，可将该元组作无歧义JSON编码后哈希，作为100字以内的 `request_id`；来源设为 `ilink`。不要仅按文字内容生成编号，同样的话可能是两次合法记录。
- Agent首次整理后先持久保存要发送的完整请求，再调用工具；网络重试重用完全相同的原话、整理结果、时间和请求号。重新让模型整理导致结果变化时，同号会返回409，而不能换号绕过去重复写账。
- 需要追问时，由 Agent 负责保存对话上下文、在微信提问和处理回答；没有明确事实前不能调用入账工具。当前API没有完整对话状态机或自动历史补录功能，不应声称已具备。
- 数据和回执持久化成功后再按通道策略确认消息和推进游标；回复失败不意味着入账失败，重试先查原回执，不重复入账。

随口记自带的 `channel.bot.ILinkBotWorker` 当前是“iLink文本 → AgentService旧规则入口 → 回复”，没有模型调用，单独启用它不会自动整理任意口语。若选择让该 worker 承担模型整理，还需要单独实现模型执行层、超时与失败处理、请求持久化及追问上下文；这些不在当前结构化API的实现中。无需同时启用两端收消息。

## 面向用户的进度和报表

`agent_policy.user_presentation` 要求调用方把接口术语翻译成业务内容。查询前说明实际选定的账本、时间和范围，例如：“正在整理糖水铺10月的营业收入、进货支出和各项费用，并核对各商品销量。”范围还没确定就先明确范围，不把 `entries / sales / summary` 当进度说明，不声称尚未执行的查询已完成。

报表按“账本与统计时间 → 收支概览 → 主要支出 → 商品销售 → 待补充信息”组织，只展示有依据的数据：

- 金额用人民币、千位分隔和两位小数；收入、采购付款、费用付款分别列出。
- 收支差额是已记收入减采购付款及费用付款，不等于利润；采购付款不等于实际耗料成本。
- 未知值写“暂无法计算”并说明缺什么，不能输出 `None` / `null` 或当作0。未记录日期不算零营业，未取完的分页不能声称完整。
- 每份报表注明统计时间、金额口径和记录覆盖情况。日总额、单品明细和派生观测不重复相加；不能把多月数据当作一个月结果。
- 微信默认发简短纯文本，先给核心数值，长明细另行展开；网页或文件可以用表格。调试字段、接口路径、拉取次数和服务器文件路径不进入主报表。
- 文件只有通过通道发送附件或提供真实可访问的链接后，才能称为已交付；`/workspace/...` 不是用户的下载地址。

固定报表和内置iLink整理层的具体产品方案见[用户可读回复与固定报表方案](report-output-design.md)。本版本提供上述机器可读展示约定，API仍返回业务JSON；它不能强制任意外部Agent遵守模板。要在产品层固定输出，需要另行实现由产品计算数据并渲染的报表接口/模板，Agent仅选择时间范围与补充解释。当前没有这类新报表生成接口，也未把iLink内置worker改成报表机器人。

## 写入结果应怎样向用户说明

`POST /v1/captures` 返回 HTTP 200，表示原话得到一个终态处理结果；是否入账必须查看响应中的 `entries` / `sales`，不能从 HTTP 状态码或 `observations` 推断。机器可读约定见 `/v1/capabilities` 的 `agent_policy.capture_result_policy`。

- 原话保存：查看 `capture`，保留用户逐字原文。结构化模式的 `normalization` 回传经校验的 Agent 整理结果，随完整幂等回执持久化；原话详情仍提供已写入的关联行。
- 财务与销量：只报告实际返回的 `entries` / `sales`。天气等 `observations` 保存成功，不等于营业额已入账。
- 未解析内容：查看 `parsed.leftovers`。`partial` 可以同时包含已成功写入的营业额和未解析叙述，不能将其一概说成“记账失败”，也不能说成“全部已记录”。
- 用户确实没有说明金额归属时才追问；“今天的营业额很差，只有1300”已经表达营业额1300，旧规则漏识别属于解析能力缺口。
- 不要把“Agent整理”实现成改写原话后用新请求号再提交文本。正确做法是在同一次 capture 中保留原话并附 `structured`。

可以向用户说：“原话已保存，今天营业额1300已入账；天气已记录，马拉松可能影响生意的判断已保留在原话中。”

## 必须遵守

- 能力状态为 `available` 才能直接使用；`planned` 只能向用户说明尚未实现，不能伪装成已执行；`unsupported` 必须明确告知边界。
- 工作空间、行业 profile、实际/计划/预算、日期、金额归属和金额口径不明确时，先追问。
- “新品售价30元”“预计花300元”“以后可能采购100斤”不能仅凭数字直接记成正式账。
- 个人微信、客如云和外卖平台直连当前都不能承诺已支持。
- 标准成本只能标为估算，不得称为实际耗料成本或实际利润。
- 当前原生 iLink worker、CLI和本地网页仍可走受控规则入口；它们本身没有模型来整理任意口语。Agent先整理的路径需由外部 Agent 显式调用带 `structured` 的API。

## 当前基础

当前实现保留 `record` 原话、`entry`/`sale`/`observation` 投影和旧 `shop_id` 兼容；profile 作为工作空间元数据和模块边界。REST 和 iLink Bot 共用 `AgentService`，工作空间必须属于服务端配置的 owner。

## 写入与重试

- `request_id` 是业务幂等键，限定在 principal、workspace 和 operation 下；同号不同内容返回 `409 idempotency_conflict`。服务端生成的 `X-Request-ID` 只作请求追踪，不能代替业务编号。
- capture、修正和导入的业务写入与完整响应在同一事务提交。相同请求重试保留原响应的内容，只把顶层 `duplicate` 设为 `true`；导入内层的 `imported` 仍表示原请求导入的行数。工作空间仍须属于当前 owner；行业 profile 后续变更或修正目标后续删除，不阻止已完成请求重放，新的写入仍校验当前 profile 和目标归属。
- 文本模式与结构化模式共用 capture 幂等域。同编号改模式、改原话或改整理结果都会冲突，不能在旧文本请求上再提交结构化内容以补写。旧文本请求的指纹与完整缓存继续兼容。
- `/healthz` 不访问数据库；`/readyz` 只读检查完整性、版本、必需表与字段，以及配置的工作空间和 worker 心跳。未初始化或缺少控制表的数据库返回 503，API 请求不会替它建表。升级/初始化需在服务停止后显式执行。
- `pending` / `parsing` 不能视为完成，返回 `409 request_in_progress` 后应使用原业务编号稍后重试。`rejected` 表示原话已保留、没有写入账目，修改原话后需要新编号。非法结构化输入在写库前报 `400 invalid_structured`，不会回退运行旧解析器。
- 旧版本如果留下“业务已提交、响应未保存”的请求，无法保证重建首次完整响应；对可识别的旧原话、修正和导入返回 `409 recovery_needs_review`，保留数据供人工核对，不重新写账或静默缓存缩减结果。即使旧认领已释放，也检查业务证据；已完成的旧请求仍重放完整缓存。仅认领后退出、尚未写入业务的旧请求可在租期过后重试。新原话和修正使用无歧义的 principal/request 编码，避免含冒号的不同组合共享业务身份。
- CSV 先调用 `/v1/imports/preview` 展示精确预览，再明确确认并调用 commit。预览绑定 principal、workspace 和 CSV 的 SHA-256，有效期1800秒，成功提交时绑定一个 request_id。过期或消费后的 token 不能用于新的提交；原提交的相同请求仍可重放缓存响应。预览同时记录当时已有的同文件批次，并用 `duplicate_file` 和 `existing_batch`（编号、文件名、行数）展示。预览之后才出现批次但本请求没有完整响应时返回 `409 recovery_needs_review`，核对后需重新预览；旧预览没有批次快照且文件已导入时也适用。
- 信息不足或能力不支持时先追问。Bot 当前只做单聊文本 capture；任务提醒、平台直连、普通个人微信和媒体处理不能被当成已完成能力。

已保存的旧 `partial` 记录不会因升级而自动补账。应先读取原记录和该日账目，确认尚无对应金额，再另行安排有原记录依据的补录；当前修正接口只能修改已有业务行，不能给只有观测的原记录增加新账目。不要用新的请求编号重复发送整段混合原话来修复历史记录。

# 补充、修正与待核对

2026-10-23。本轮在现有本地网页上实现四件事：记录结果卡、待核对清单、补充缺失信息、修正原记录。下面是实际行为、数据落点和边界。

## 一句话规则

**补充和修正都写回原来那一行账目，不新增一笔；每次改动本身留一条原话，改了什么、依据什么都能翻出来。**

原话（`record.raw_text`）不会被改写。修正不会重新解析原话，也不会产生第二笔收支。

## 网页上的四个地方

| 位置 | 做什么 |
| --- | --- |
| 记录结果卡 | 提交后显示这次实际写下的账目/销量行、另外记下的经营信息、原始原话；每行带「修正」按钮 |
| 待核对（标签页，带数量角标） | 只列会影响算账、且补一句就能定下来的缺口 |
| 修正编辑器 | 从结果卡、账目明细、销量明细或待核对清单打开；缺的字段标「（缺）」并自动聚焦 |
| 改动历史 | 同一行改过几次、每次改了哪些字段、依据是哪句话 |

结果卡只描述「写下那一刻」的内容；如果其中某行之后被改过，卡片会补一句「最新数值以账目明细为准」。

## 待核对清单列什么

只列四类缺口，因为这几类会直接改变算出来的数：

| 情况 | 提示 |
| --- | --- |
| 采购没有数量 | 采购还缺数量，暂时算不出原料单价 |
| 支出没有费用归属月 | 费用还缺归属月份 |
| 销量没有金额 | 销量还缺金额 |
| 销量没有平台 | 销量还缺平台 |

不列「原话没识别出内容」这类：那不是缺字段，得重新记一句。清单按全部月份统计，不受月份筛选影响；已经填齐的行会自动从清单里消失。

## 数据落点

修正本身是一条原话记录：

| 字段 | 值 |
| --- | --- |
| `record.source` | `review` |
| `record.parse_status` | `correction` |
| `record.raw_text` | 你填的改动依据（1–500 字） |
| `record.dedup_ref` | `review:<request_id>` |
| `record.correction_of` | 被改的行，如 `entry:e_xxx` / `sale:s_xxx` |
| `record.correction_detail` | JSON：`{before, after, source_record_id}` |

`before` 只含真正改动过的字段，`after` 是改动后的值，`source_record_id` 指向产生这行账目的最初原话。

修正记录**不写** `ledger_refs`：`ledger_refs` 的语义是「这行账目由哪条原话产生」，改一行账目的原话不是它的产生者。被改行的来源仍然通过 `record_for_origin` 指向最初那条原话。

Schema 版本 3 → 4，只新增两列和一个索引，旧库用 `ALTER TABLE` 补列，旧数据、原话关联和已有观测都不动。

## 幂等与重复入账

- 每次打开编辑器生成一个 `request_id`，同一次改动重试沿用同一个编号；重复提交返回 `duplicate: true`，不再改第二遍，即使第二次带了不同的值。
- 并发同号请求由 `record(shop_id, dedup_ref)` 唯一索引挡下，捕获 `IntegrityError` 后按重复处理。
- 一次修正里的原话写入、字段更新、观测重投影在同一个事务里；投影失败则原话和字段一起回滚，不会留下半条修正。
- 修正会重新投影该行的观测（`entry:<id>:` / `sale:<id>:`），先删后加，不产生重复观测，观测仍挂在最初那条原话上。

## 金额和字段校验

只接受白名单字段；金额和数量必须是非负有限数，日期 `YYYY-MM-DD`，费用归属月 `YYYY-MM`，金额口径 `gross|settlement`，记录粒度 `daily|transaction`，账目类型 `revenue|purchase|expense`，文字字段不超过 100 字。依据必填。修正后与当前值完全相同会直接报错，不写空修正。

销量改商品名时先按别名归一到规范商品，再写 `product_id` / `product_category`，和录入、导入走同一套归一逻辑。

## 顺带修掉的重复入账陷阱

`牛肉面卖了30份300元` 原先会变成两笔：一笔「其他支出 300 元」和一条「销量 30 份、金额待补充」。补上销量金额后就重复计了 300 元。现在规则是：

- 销量后面紧贴的金额（可隔一个逗号/顿号，可带「共/一共/总共/合计」）算这笔销量的合计；
- 中间隔着别的字就不认领 —— `牛肉面卖了30份，买了牛肉300元` 仍然是销量 30 份（金额待补充）加一笔 300 元进货；
- 只有写明「一份/每份/单价」时后面的数才是单价（`牛肉面卖了30份，一份12块` → 360 元），这条和原来一致；
- `卖了30份牛肉面300元` 的商品名不再把「300元」吞进去。
- 2026-10-24 补齐连续销量与无分隔费用；显式「共300元」与歧义「300元交房租8000」按不同规则处理。后者只记房租8000、销量金额待补，300元作为未识别片段在结果卡/CLI提示，不生成额外费用或新的待核对行。完整例子与不猜测边界见[连续口语解析约定](parser-boundaries.md)。

## 接口

`POST /api/review`，JSON：

```json
{"request_id": "…", "target_id": "sale:s_xxx", "fields": {"amount": 300, "platform": "美团"}, "reason": "美团卖了30份共300"}
```

返回 `{review: {duplicate, record, target_id, changed, history}, state}`。`/api/records` 的响应新增 `written`（这次实际写入的 entry/sale 行），结果卡据此渲染。`/api/state` 新增 `review`（待核对清单，含 `missing` 字段名与 `history`）。

## 边界

- 没有「撤销修正」和「删除账目」的界面；改错了只能再改一次，两次都会留在历史里。
- 不重新解析原话：改日期、改类型都不会让这句话再生成别的账目。
- 原话列表最多显示最近 100 条；更早的修正依据仍在库里，但页面上看不到。
- 观测重投影会覆盖该行原有的派生观测；历史观测值不单独留档，旧值以 `correction_detail.before` 为准。
- 仍只覆盖本地 SQLite 与单机单用户网页；没有并发多端写入保证，没有库存实际计价、退款和跨月自动分摊。

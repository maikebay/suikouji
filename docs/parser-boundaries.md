# 连续口语解析：金额归属与随想边界

2026-10-26，0.2.0-staging。适用于 CLI、原生 iLink、无 structured 的 capture 与本地网页共用的 Python 文本录入入口；不适用于旧 `index.html → parser.js → localStorage` 原型。Agent 传入 structured 时只校验和保存，不运行这些规则，校验失败也不回退。

## 核心约定

- 一个金额只能属于一条销量或一笔账目；无法确定的金额留在 `leftovers`，不复制成额外收支。
- 日期、费用归属月、采购数量先排除，再判断金额。`200人工` 的「人」、`8000包装80` 的「包」不是数量单位；完整分类词优先，`买了三包调料80` 仍保留采购数量。
- 原话完整保存在 `record.raw_text`；销量 `start:end` 是原文中的不重叠片段，不通过重建句子推算索引。
- 日期按原文顺序继承，新的显式日期只影响它之后的事件；平台、渠道不从上一条销量自动继承。费用归属月只属于本条费用，与付款日期独立。
- 同一请求号重试只返回已存结果，不按新的正文再记一次。不同请求号不按正文相同自动合并；本轮不新增多端并发保证。

## 有限随想识别

随想是独立记事，保存正文、归档日、逐字来源和可选标签，不计入财务、不要求 `assertion`，不划分 idea/opinion/plan，不生成任务或提醒。原生规则仅覆盖明确标记和少量句首模式；任意经营感受、多句自由续写仍优先由外部 Agent 整理，不能把以下样例扩大为通用意图识别。

| 原话 | 原生入口边界 |
| --- | --- |
| 记个想法：下周想推芋圆新品。#新品 | 识别明确随想标记，中文或英文冒号均可；只提取明确 `#标签`，标题省略 |
| 记个随想：明天试南瓜甜品 | 识别明确随想标记；无标签照常保存，不追问 |
| 明天想试南瓜甜品 | 支持明确句首“明天想试…”模式 |
| 下周想推新品芋圆 | 支持明确句首“下周想推新品…”模式 |
| 今天营业额1300元。记个想法：明天试南瓜甜品 #新品 | 明确营业额与随想分别保存 |
| 记个想法：下周试南瓜甜品。今天营业额1300元 | 随想不吞掉句号后的明确营业额，支持相反顺序 |
| 记个想法：下周预算300元，新品想卖12元 | 数字只留随想正文，不成为支出、收入或销量 |
| 生意还可以，老顾客非常多 | 记为定性观测：生意/好坏=还可以，客流/情况=老客多；不编人数、占比或金额，也不当成随想 |
| 这条随想记在昨天：试南瓜甜品 | 原生入口不处理另指定归档日，保留并说明需要外部 Agent；不得默认为今天 |

当前标记只在句首或逗号后识别“记个想法/记个随想 + 冒号”。无标记的句首模式为“明天/下周 + 可选我 + 想试/试做/想做/打算试/打算做/试”、“明天/下周 + 可选我 + 想推 + 最多12个中文/字母/数字 + 新品”，以及“今天想到/昨天想到”。这些是固定语法，其他同义写法不据此承诺。

餐饮原话里的常见定性说法由观测词表认领，不进 leftovers，也不编数字：客流「情况」只取老客多、人多、客人少、客流一般；生意「好坏」只取还可以、不错、一般、不好。例如「老顾客非常的多」记老客多，「生意还可以」「生意有点差」分别记还可以、不好。明确的「客流120人」「上座20桌」仍是人数和桌数。否定、假设和问句不记成已发生观测。「可能影响生意」「生意差不多」「天气很好」不在这组词表里，不能猜成生意好坏、人数或晴天。观测不回加财务。

先定位随想原文范围，再隔离内部金额、日期和数量；财务和观测只处理其余可确定片段。随想正文里的「生意还可以」仍只属于随想，不另拆观测。中文句号、分号、问叹号、换行和非小数的英文句号后独立判断；识别出的 Markdown 链接、网址及行内代码内部标点保持原文，不作为句界。标记只覆盖当前句，跨句正文不自动合并，仅紧随的纯 `#标签` 段可以接到前一随想。因此“记个想法：试南瓜。可以搭配木薯银耳。”的第二句不能承诺自动合并，应保留未解析并交 Agent；无句界的同句财务片段也不承诺能与随想准确分离。

正文取原文切片，仅去掉末尾明确标签串；`source_quote` 保留包含标签的连续来源。标签无效或正文为空时，该候选随想不保存，原句留未解析并提示。识别到另归档日指令时，本消息的候选随想统一留待外部 Agent 整理，其他可确定财务片段仍按受控规则处理。具体模式见 `engine/thoughts.py`，不能用结构化示例证明原生规则理解同样的全部口语。

## 随想归档日与正文时间

随想默认归档在首次收到消息的工作空间时区日期，Asia/Shanghai 只是部署默认值。收到“记个想法：明天试新品”或“记个想法：昨天想到下周推新品”，都归收到当天，昨天、明天、下周保留在正文；跨午夜同号重试不得重算。只有明确要求另一个归档日时，才由外部 Agent 澄清并提交严格合法 `thought.date`；非法或冲突的归档日不得悄悄换成今天。

随想正文中的未来时间不改变混合原话既有账目/观测的事件日期算法；纯随想 capture 取随想记录日期最大值。随想列表按 `thought.date` 检索，原话时间线仍按 capture 事件时间过滤。下文的顺序日期规则适用于随想范围之外的财务/观测，不把正文里的时间解释为任务执行日。

## 近似金额不能精确入账

“大概做了1300”“花了两百多”“可能收入一千左右”保留为未解析金额片段，不自动写成精确1300、200或1000；同句其他明确账目、受控观测或明确随想仍可保存。跨换行的“两百↵多”及“大概做了↵昨天↵1300元”（↵表示换行）仍保留不确定性；“客流10人左右收入1300元”只保存明确收入。“营业额1300元计划收入100元”只保存实际1300，后面的设想为未解析内容。受控天气“多云”不作为金额的“多”后缀。这些保护覆盖列明的近似表达及受控边界，不承诺识别所有自然语言不确定表达。

`partial` 回执先说已保存什么，再说明哪部分未入账并追问。已经完成的 partial 没有用一句“直接记”安全补写旧原话的接口；禁止换号重发整段。未知网络结果先按同编号、同完整请求重试核对回执，不能猜成写入失败。

## 营业额描述与后续金额

0.1.1-staging 增加受控的营业额续句识别：“今天的营业额很差，只有1300”中的后半句继续说明前半句的日营业额，不应因逗号而漏记，也不能兜底成其他支出。完整原文保留不变，财务账只增加一笔日营业额1300。

这不等于让任意金额继承上一句分类：新的费用、日期、平台、数量，或预测、假设、问句、否定及多个待选择金额，都不能通过此续句规则被猜成营业额。句号等明确句子边界不沿用分类；更自由的自然语言仍在受控规则之外。

用户截图还包含天气、周末、马拉松和生意评价。受控天气可生成独立观测；「生意还可以」「老客多」这类定性说法也生成观测，不再只因它们留在 leftovers。真正没认领的叙述仍留在 `leftovers`，所以营业额已入账时整条原话仍可能为 `partial`。回执用 `coverage` 区分：经营要点已经记下，partial 只表示还有未结构化原话。天气或马拉松“可能影响生意”只是原话中的推测，不能生成已证实的因果结论，也不要写成生意好坏。HTTP 200 和 `partial` 的报告方式见[Agent 回执约定](agent-capabilities.md#写入结果应怎样向用户说明)。

同请求号重试保持首次完整响应，不因新解析规则而自动重算。旧记录漏记的金额需要先核对再补录，本次不批量重解析历史原话或修改服务器账本。

## 连续销量

从左到右先定位每个「销售动词 + 数量 + 单位」，再识别该笔商品与金额，避免两种语序的正则互相抢同一数量。

| 原话 | 实际含义 |
| --- | --- |
| 卖了30份牛肉面卖了20份炒饭 | 牛肉面30份、炒饭20份；金额分别待补 |
| 牛肉面卖了30份300元炒饭卖了20份200元 | 两条销量，合计分别300、200元；没有额外支出 |
| 卖了30份牛肉面300元炒饭卖了20份200元 | 数量在前与商品在前可混用，金额仍各归本笔 |
| 牛肉面卖了30份每份12元炒饭卖了20份每份10元 | 明确单价，金额分别360、200元；不要求先加逗号 |
| 昨天美团外卖牛肉面卖了30份300元今天饿了么自取炒饭卖了20份200元 | 两笔分别保留自己的日期、平台和渠道 |
| 今天营业额1280牛肉面卖了30份300元 | 保留营业额1280与销量300；不在解析层把两种口径相加 |
| 买了50斤牛肉花了680牛肉面卖了30份 | 保留采购50斤/680元与销量30份；采购金额不被销量遮掉 |

只有「一份/每份/单价/单件/每个」明确引出的金额是单价；紧贴数量或商品后的「300元」是整笔合计。允许零个或一个逗号/顿号。`共/一共/总共/合计/总计/共计/拢共/统共` 是显式合计标记，也支持「合计是」；数量在前的「每份卖12元」仍是单价。平台/渠道既可在动词前，也可在数量与商品之间。

同一销量已认领单价或合计后，再出现紧邻金额，不兜底成支出，也不静默覆盖：`卖了30份牛肉面每份12元合计400元` 暂按明确单价记360，`合计400元` 留作未识别，整体partial；即使后一个合计也是360，本轮也保留待核对，不声称完成多金额一致性推理。

## 销量与后续费用的交界

| 原话 | 处理 |
| --- | --- |
| 牛肉面卖了30份共300元买了牛肉680 | 销量合计300；另一笔采购680 |
| 牛肉面卖了30份300元房租8000水电200 | 房租、水电各有自己的金额；销量300、房租8000、水电200 |
| 牛肉面卖了30份300元交房租8000 | 300的归属不明：销量金额待补、只记房租8000，300元留作未识别 |
| 牛肉面卖了30份，300元成本 | 300元明确后置「成本」：记采购，不当销量合计 |
| 牛肉面卖了30份，500块交房租 | 房租没有另一个金额：500归房租，销量金额待补 |
| 牛肉面卖了30份，买了牛肉300元 | 采购300；销量金额待补 |

显式「共300」与裸「300元交…」不同。支付动词可能是在解释前置金额，因此后一种写法不靠猜测认领。要消除歧义，可明确写成「牛肉面30份共300元，交房租8000元」。

## 连续费用与采购

分段依据是独立记账锚点，不是类型优先级是否改变；水电、人工、房租即使都是 expense，也不能沿用第一个分类。

| 原话 | 实际含义 |
| --- | --- |
| 房租8000水电200人工600 | 房租8000、水电200、人工600 |
| 交房租8000付水电200发工资600 | 同上，支付动词不粘到上一笔摘要 |
| 房租8000房租9000 | 两个明确房租锚点，保留两笔，不按分类相同合并 |
| 房租八千水电二百 | 中文金额与阿拉伯数字的归属一致 |
| 买了50斤牛肉花了680交房租8000买了三箱啤酒花了240水电200 | 两笔采购、两笔费用；采购数量、品名、金额不串行 |
| 昨天付11月房租8000今天交10月水电200 | 昨天付的11月房租、今天付的10月水电；月份不成为金额 |
| 10月8000元房租11月9000元水电 | 月份、金额都在分类前也可连续记：10月房租8000、11月水电9000 |
| 营业额1280元300元成本 | 营业额1280、后置成本300；成本不覆盖更早的营业额 |
| 交房租300元8000 | 一个房租锚点只认领第一个后置金额300；8000未识别，不再复制出第二笔租金 |

一个分段内最多认领一个金额：分类后有金额时取第一个；只有前置金额时取离分类最近的一个。其他金额保留为未识别。多笔费用请分别说明分类或加明确分隔，不从一串金额推测交易数。`房租8000人手600`、`水电200包80` 不扩充模糊分类别名，只保留已明确的房租8000/水电200，将600/80作为未识别金额。

## 明确日期不能被改写

- 显式ISO日期、中文年月日/月日、日号必须是有效公历日期。`2026-02-30`、`2月31日`、非闰年基准下的`2月29日`报「日期不合法」，不会退回今天或把29日解释为当月29日。
- 有显式年份就用原文年份；无年份用本条原话保存的解析基准年，单独日号再用基准月。因此`2024年2月29日`有效，基准年2024下的`2月29日`也有效；日期相关辅助函数沿用同一个基准，不偷偷使用机器当前年份。
- 原话、非金额观测与账目/销量共用顺序日期扫描。`2024年2月29日客流10人牛肉面卖了30份300元房租8000`的原话日期、客流、销量和房租都为2024-02-29；不能只修账目而让客流落到今天。每条事件取它之前最近的日期；单条原话的`occurred_at`取全句最后一个有效日期，不代表所有事件都在那一天。日期后的费用月份仍只改变归属月，不改变事件付款日。
- 随想范围之外的财务/观测片段包含非法日期时，整个文本请求拒绝：先保留原话，再将状态写为`rejected`，不写任何投影，包括同句其他合法片段。本地兼容 `/api/records` 返回JSON 400；认证 `/v1/captures` 的终态回执按其状态合同处理，不能只看HTTP码。同一请求号换正文重试不能重新写入，需纠正日期后使用新的真实原话和请求号。
- CLI也不写账，返回非零退出码；当前CLI仍直接显示ValueError堆栈，未在本轮改造统一JSON错误呈现。
- 这里的拒绝不同于`partial/leftovers`：明确非法日历日期不是可用今天代替的缺省字段。

## 不猜商品分界

`卖了30份牛肉面炒饭卖了20份` 没有依据确定「牛肉面炒饭」是一个商品，还是两笔商品名粘在一起。整段不生成销量或账目，保留未识别。加入逗号、日期或平台等明确边界后，才分别识别：

- `卖了30份牛肉面，炒饭卖了20份`
- `卖了30份牛肉面今天炒饭卖了20份`
- `卖了30份牛肉面美团炒饭卖了20份`

`卖了30份卖了20份炒饭` 第一笔缺商品，留作未识别；第二笔炒饭20份可记录，30份不变成金额。

## 未识别内容在哪里呈现

- 有已识别行，同时还有 `leftovers`：原话状态为 `partial`。
- 网页结果卡显示「这句里还没识别：…」；CLI 显示「没看懂的片段：…」。
- 「待核对」标签页仍只列采购缺数量、费用缺归属月、销量缺金额/平台，不自动为每个未识别片段新建待核对行。
- 已写下的销量缺金额时，可在原行补齐；不重新提交整句来重复生成已识别部分。原话保留，但本轮没有自动重解析未识别片段或把它们补写入原记录的接口。

## 证据与覆盖范围

以下213项及耗时是2026-10-24财务解析改动的历史验证记录，不是0.2.0-staging随想功能的最新验收结果。当前版本需另验随想两种混合顺序、正文金额隔离、归档时区、近似金额、无标签和旧回执兼容；离线测试不能代替真实 iLink、Docker 或任意外部 Agent 的对话验收。

- [专门边界回归](../tests/test_parser_boundaries.py)：两种销量语序及混用、中文金额、单价、精确 span、日期/平台/渠道隔离、费用分类/重复分类、采购数量、归属月份、显式合计、歧义金额与商品分界、SQLite 来源、同号换正文重试、标点不变性。
- [真实 HTTP 回归](../tests/test_web.py)：`written` 四行及同号重试、歧义金额的 `partial/leftovers` 与已存状态、月份前置两笔独立归属、非法日期JSON 400且原话rejected/零投影、显式年份下原话/客流/销量/费用日期一致。

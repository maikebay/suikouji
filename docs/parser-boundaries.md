# 连续口语解析：金额归属与不确定边界

2026-10-24。适用于当前本地网页 `/api/records`、CLI `record` 共用的 Python 解析入口；不适用于旧 `index.html → parser.js → localStorage` 原型。

## 核心约定

- 一个金额只能属于一条销量或一笔账目；无法确定的金额留在 `leftovers`，不复制成额外收支。
- 日期、费用归属月、采购数量先排除，再判断金额。`200人工` 的「人」、`8000包装80` 的「包」不是数量单位；完整分类词优先，`买了三包调料80` 仍保留采购数量。
- 原话完整保存在 `record.raw_text`；销量 `start:end` 是原文中的不重叠片段，不通过重建句子推算索引。
- 日期按原文顺序继承，新的显式日期只影响它之后的事件；平台、渠道不从上一条销量自动继承。费用归属月只属于本条费用，与付款日期独立。
- 同一请求号重试只返回已存结果，不按新的正文再记一次。不同请求号不按正文相同自动合并；本轮不新增多端并发保证。

## 连续销量

从左到右先定位每个「销售动词 + 数量 + 单位」，再识别该笔商品与金额，避免两种语序的正则互相抢同一数量。

| 原话 | 实际含义 |
| --- | --- |
| 卖了30份牛肉面卖了20份炒饭 | 牛肉面30份、炒饭20份；金额分别待补 |
| 牛肉面卖了30份300元炒饭卖了20份200元 | 两条销量，合计分别300、200元；没有额外支出 |
| 卖了30份牛肉面300元炒饭卖了20份200元 | 数量在前与商品在前可混用，金额仍各归本笔 |
| 牛肉面卖了30份每份12元炒饭卖了20份每份10元 | 明确单价，金额分别360、200元；不要求先加逗号 |
| 昨天美团外卖牛肉面卖了30份300元今天饿了么自取炒饭卖了20份200元 | 两笔分别保留自己的日期、平台和渠道 |
| 今天营业额1280牛肉面卖了30份300元 | 保留营业额1280与销量300；不在解析层把两种口径相加 |
| 买了50斤牛肉花了680牛肉面卖了30份 | 保留采购50斤/680元与销量30份；采购金额不被销量遮掉 |

只有「一份/每份/单价/单件/每个」明确引出的金额是单价；紧贴数量或商品后的「300元」是整笔合计。允许零个或一个逗号/顿号。`共/一共/总共/合计/总计/共计/拢共/统共` 是显式合计标记，也支持「合计是」；数量在前的「每份卖12元」仍是单价。平台/渠道既可在动词前，也可在数量与商品之间。

同一销量已认领单价或合计后，再出现紧邻金额，不兜底成支出，也不静默覆盖：`卖了30份牛肉面每份12元合计400元` 暂按明确单价记360，`合计400元` 留作未识别，整体partial；即使后一个合计也是360，本轮也保留待核对，不声称完成多金额一致性推理。

## 销量与后续费用的交界

| 原话 | 处理 |
| --- | --- |
| 牛肉面卖了30份共300元买了牛肉680 | 销量合计300；另一笔采购680 |
| 牛肉面卖了30份300元房租8000水电200 | 房租、水电各有自己的金额；销量300、房租8000、水电200 |
| 牛肉面卖了30份300元交房租8000 | 300的归属不明：销量金额待补、只记房租8000，300元留作未识别 |
| 牛肉面卖了30份，300元成本 | 300元明确后置「成本」：记采购，不当销量合计 |
| 牛肉面卖了30份，500块交房租 | 房租没有另一个金额：500归房租，销量金额待补 |
| 牛肉面卖了30份，买了牛肉300元 | 采购300；销量金额待补 |

显式「共300」与裸「300元交…」不同。支付动词可能是在解释前置金额，因此后一种写法不靠猜测认领。要消除歧义，可明确写成「牛肉面30份共300元，交房租8000元」。

## 连续费用与采购

分段依据是独立记账锚点，不是类型优先级是否改变；水电、人工、房租即使都是 expense，也不能沿用第一个分类。

| 原话 | 实际含义 |
| --- | --- |
| 房租8000水电200人工600 | 房租8000、水电200、人工600 |
| 交房租8000付水电200发工资600 | 同上，支付动词不粘到上一笔摘要 |
| 房租8000房租9000 | 两个明确房租锚点，保留两笔，不按分类相同合并 |
| 房租八千水电二百 | 中文金额与阿拉伯数字的归属一致 |
| 买了50斤牛肉花了680交房租8000买了三箱啤酒花了240水电200 | 两笔采购、两笔费用；采购数量、品名、金额不串行 |
| 昨天付11月房租8000今天交10月水电200 | 昨天付的11月房租、今天付的10月水电；月份不成为金额 |
| 10月8000元房租11月9000元水电 | 月份、金额都在分类前也可连续记：10月房租8000、11月水电9000 |
| 营业额1280元300元成本 | 营业额1280、后置成本300；成本不覆盖更早的营业额 |
| 交房租300元8000 | 一个房租锚点只认领第一个后置金额300；8000未识别，不再复制出第二笔租金 |

一个分段内最多认领一个金额：分类后有金额时取第一个；只有前置金额时取离分类最近的一个。其他金额保留为未识别。多笔费用请分别说明分类或加明确分隔，不从一串金额推测交易数。`房租8000人手600`、`水电200包80` 不扩充模糊分类别名，只保留已明确的房租8000/水电200，将600/80作为未识别金额。

## 明确日期不能被改写

- 显式ISO日期、中文年月日/月日、日号必须是有效公历日期。`2026-02-30`、`2月31日`、非闰年基准下的`2月29日`报「日期不合法」，不会退回今天或把29日解释为当月29日。
- 有显式年份就用原文年份；无年份用本条原话保存的解析基准年，单独日号再用基准月。因此`2024年2月29日`有效，基准年2024下的`2月29日`也有效；日期相关辅助函数沿用同一个基准，不偷偷使用机器当前年份。
- 原话、非金额观测与账目/销量共用顺序日期扫描。`2024年2月29日客流10人牛肉面卖了30份300元房租8000`的原话日期、客流、销量和房租都为2024-02-29；不能只修账目而让客流落到今天。每条事件取它之前最近的日期；单条原话的`occurred_at`取全句最后一个有效日期，不代表所有事件都在那一天。日期后的费用月份仍只改变归属月，不改变事件付款日。
- 一句包含非法日期时，整个请求拒绝：先保留原话，再将状态写为`rejected`，不写任何账目、销量或经营观测，包括同句其他合法片段。HTTP返回JSON 400；同一请求号换正文重试也不重新写入，需修改日期并使用新请求号。
- CLI也不写账，返回非零退出码；当前CLI仍直接显示ValueError堆栈，未在本轮改造统一JSON错误呈现。
- 这里的拒绝不同于`partial/leftovers`：明确非法日历日期不是可用今天代替的缺省字段。

## 不猜商品分界

`卖了30份牛肉面炒饭卖了20份` 没有依据确定「牛肉面炒饭」是一个商品，还是两笔商品名粘在一起。整段不生成销量或账目，保留未识别。加入逗号、日期或平台等明确边界后，才分别识别：

- `卖了30份牛肉面，炒饭卖了20份`
- `卖了30份牛肉面今天炒饭卖了20份`
- `卖了30份牛肉面美团炒饭卖了20份`

`卖了30份卖了20份炒饭` 第一笔缺商品，留作未识别；第二笔炒饭20份可记录，30份不变成金额。

## 未识别内容在哪里呈现

- 有已识别行，同时还有 `leftovers`：原话状态为 `partial`。
- 网页结果卡显示「这句里还没识别：…」；CLI 显示「没看懂的片段：…」。
- 「待核对」标签页仍只列采购缺数量、费用缺归属月、销量缺金额/平台，不自动为每个未识别片段新建待核对行。
- 已写下的销量缺金额时，可在原行补齐；不重新提交整句来重复生成已识别部分。原话保留，但本轮没有自动重解析未识别片段或把它们补写入原记录的接口。
